# mall-api 错误预算政策（模板）

> 这份政策要由研发负责人、产品负责人、SRE 负责人三方签字才生效。没签字的政策，预算用完时没人会真的停发布。

## 1. 适用范围

| 项目 | 内容 |
|---|---|
| 服务 | mall-api（商城后端） |
| SLO | 可用性：30 天内 `/api/` 请求非 5xx 比例 >= 99.9%；延迟：30 天内 `/api/` 请求 500ms 内完成的比例 >= 99% |
| 统计窗口 | 滚动 30 天 |
| 数据来源 | Prometheus 记录规则 `slo:error_budget_remaining:ratio`，大盘“mall-api SLO 与错误预算” |
| 生效日期 | YYYY-MM-DD |
| 复审周期 | 每季度一次 |

## 2. 预算状态和对应动作

| 剩余预算 | 状态 | 发布 | 其他动作 |
|---|---|---|---|
| > 50% | 正常 | 正常发布，可以做有风险的实验（新功能灰度、架构调整） | 无 |
| 25% ~ 50% | 关注 | 正常发布，但每次发布必须走灰度，观察 30 分钟 | SRE 在周会上通报消耗原因 |
| 0 ~ 25% | 警戒 | 只允许低风险发布（配置、文案、修 bug），大版本推迟 | 研发拿出 20% 人力处理稳定性问题 |
| <= 0（耗尽） | 冻结 | **冻结功能发布**，只允许修复稳定性、安全漏洞的变更 | 召开复盘会；给出改进项和负责人；直到滚动 30 天预算回正才解冻 |

## 3. 冻结期间的例外

以下情况可以在冻结期发布，需要研发负责人和 SRE 负责人两人审批，记录在变更单里：

- 修复正在造成 5xx 或超时的 bug
- 安全漏洞修复
- 法律、合规要求的变更
- 对营收影响重大、且业务负责人书面确认愿意承担风险的变更（一个季度最多 1 次）

## 4. 不计入预算的情况

- 计划内维护，并且提前 3 个工作日通知了用户
- 上游第三方故障（如支付渠道），且 mall-api 已按设计降级。降级没生效的仍然计入
- 压测、故障演练期间带压测标记的流量（SRE-2、SRE-4）

不计入的时间段要在复盘文档里写清楚，并用 Prometheus 规则或大盘注释标出来，不能事后口头扣除。

## 5. 单次故障消耗过大

单次故障烧掉超过 20% 的 30 天预算，不管剩余多少，都必须：

1. 5 个工作日内完成复盘（时间线、根因、影响、改进项）
2. 至少一条改进项是 P0，在下一个迭代完成

## 6. 分歧处理

对预算计算方式、是否计入有分歧时，先按计入处理，然后升级到技术总监裁决。
