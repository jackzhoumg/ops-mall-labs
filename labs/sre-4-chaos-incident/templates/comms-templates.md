# 事故沟通模板

原则：说事实、说影响、说下一步、说下次更新时间。不猜原因，不甩锅，不写“应该没问题”。

## 1. 内部首次通报（事故群 / 值班群，发现后 15 分钟内）
```
【P1 事故】商城下单失败 - 处理中
开始时间：2026-11-24 14:05（告警时间）
影响：全部用户打开商城返回 503，无法浏览和下单
当前状态：已拉起事故响应。指挥官：张三，执行：李四，沟通：王五
已做：确认 mall-api 全部 Pod NotReady，正在排查
下一步：先止损（回滚 / 扩容 / 摘除故障依赖），再定位
下次更新：14:30 前
```

## 2. 内部进展更新（P1 每 15 分钟，P2 每 30 分钟，没有进展也要发）
```
【P1 事故】商城下单失败 - 更新 #2（14:30）
影响：不变 / 已缓解（错误率从 100% 降到 5%）
新发现：数据库方向网络延迟约 1.5 秒，mall-api 就绪探针超时
已做：14:22 调大就绪探针超时，2 个 Pod 恢复 Ready
下一步：联系网络负责人排查 lab-db1 方向链路
下次更新：14:45 前
```

## 3. 对外公告（客服 / 状态页，只写用户关心的，不写内部细节）
```
【服务异常通知】
14:05 起，部分用户访问商城时出现页面无法打开、下单失败的情况。
我们已定位到问题并在全力处理，预计 15:00 前恢复。
已下单用户的订单和支付不受影响。给您带来不便，非常抱歉。
下次更新：14:45 前
```

## 4. 恢复通报
```
【已恢复】商城下单失败
恢复时间：14:41（持续 36 分钟）
影响：14:05-14:41 全部用户无法访问商城，约 X 笔订单失败
止损方式：调整 mall-api 就绪探针；数据库方向网络恢复
后续：48 小时内完成复盘，复盘文档链接稍后发出
```

## 5. 演练通知（演练开始和结束各一条，避免被当成真实事故）
```
【故障演练】ops-mall 预发环境 14:00-15:00
范围：mall 命名空间 mall-api，注入网络延迟 / 杀 Pod
期间相关告警属于演练，值班同学按事故流程处理并记录
中止联系人：演练负责人 赵六
```
