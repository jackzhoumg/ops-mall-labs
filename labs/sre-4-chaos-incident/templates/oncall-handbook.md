# On-call 值班手册（ops-mall 示例）

## 1. 排班
- 一线（primary）+ 二线（secondary）两层，按周轮换，周一 10:00 交接（避开周末交接）。
- 每人连续值班不超过 1 周，两次值班之间至少隔 2 周。团队少于 4 人时，一线白天由开发轮值，夜间由运维值。
- 排班表放在共享日历和值班工具里，换班要双方确认并在群里同步。
- 值班补偿要写进制度：调休或值班补贴。没有补偿的值班制度长不了。

| 周次 | 一线 | 二线 | 升级联系人（三线） |
|---|---|---|---|
| 第 1 周 | 运维 A | 开发 B | 技术负责人 |
| 第 2 周 | 开发 B | 运维 C | 技术负责人 |
| 第 3 周 | 运维 C | 运维 A | 技术负责人 |

## 2. 升级（告警没人接时怎么办）
| 时间 | 动作 |
|---|---|
| 0 分钟 | 告警发到值班群 + 一线电话 / 短信 |
| 5 分钟没有 ack | 再次电话一线，同时通知二线 |
| 15 分钟没有 ack | 电话二线和三线（技术负责人） |
| P1 | 一线 ack 后 15 分钟内没止损，主动拉指挥官，不要一个人扛 |

工具：Alertmanager（Lab 09）按 severity 路由，P1/P2 走电话（云厂商语音通知 / 值班平台），P3/P4 走群消息。

## 3. 值班职责
- 响应告警：ack、判断级别、按 incident-levels.md 处理。
- 记录：每条告警在值班记录里写一行（时间、告警、处理、是否误报）。
- 不做和值班冲突的事：值班期间不做大变更、不出远门、手机电脑随身。
- 误报也要处理：连续误报的告警当场建工单优化，否则下次没人信告警。

## 4. 交接（每周一 10:00，15 分钟）
交接清单：
- 本周告警数量、P1/P2 事故列表、未关闭的事故和改进项
- 进行中的变更、已知风险（证书快过期、磁盘快满）
- 临时措施（手工扩容、临时关闭的告警）以及什么时候撤
- 值班工具、权限是否正常（新一线自己测一次能收到电话）

## 5. 事故响应角色
| 角色 | 职责 | 不做什么 |
|---|---|---|
| 事故指挥官（IC） | 定级、分工、决策（回滚还是继续查）、控制节奏、决定何时宣布恢复 | 不亲自敲命令排查 |
| 沟通负责人 | 按模板对内对外发通报，挡住“问进展”的人，记录时间线 | 不参与技术决策 |
| 执行 / 技术负责人 | 排查、止损操作，操作前在群里说一声，操作后报告结果 | 不自己决定对外说什么 |
| 记录员（可由沟通兼任） | 记录每个时间点、发现、操作、决策 | |

小事故一个人可以兼多个角色；P1 至少分出指挥官和执行两个人。

## 6. 处理原则
1. 先止损，后定位。能回滚就回滚，能切流量就切流量，能扩容就扩容。根因留到恢复后再查。
2. 最近有变更，先怀疑变更。打开发布记录（ArgoCD / Jenkins）看最近 2 小时谁发了什么。
3. 每个操作先说再做，做完报结果。避免两个人同时改同一个东西。
4. 保留现场：止损前如果来得及，先 kubectl describe / logs 存一份，或者留一个故障 Pod 摘掉流量不删。
