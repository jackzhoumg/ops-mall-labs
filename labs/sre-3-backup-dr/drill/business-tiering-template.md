# 业务分级与 RTO / RPO 目标（模板）

> RTO（恢复时间目标）：故障发生到业务恢复，最长能接受多久。
> RPO（恢复点目标）：恢复后最多能接受丢失多长时间的数据。
> 目标由业务方和技术方一起定，并且要有对应的预算：RTO / RPO 每往下降一个数量级，成本往往翻几倍。

## 1. 分级标准

| 级别 | 定义 | RTO | RPO | 典型容灾方式 | 演练频率 |
|---|---|---|---|---|---|
| T0 核心交易 | 不可用直接损失收入或违反监管 | <= 15 分钟 | 0 ~ 1 分钟 | 同城双活 / 多可用区 + 半同步复制或强一致集群，自动切换 | 每季度 |
| T1 重要业务 | 不可用影响大量用户体验，可短时降级 | <= 1 小时 | <= 5 分钟 | 多可用区主备 + 手动 / 半自动切换，binlog 实时备份 | 每半年 |
| T2 一般业务 | 内部系统、非实时功能 | <= 4 小时 | <= 1 小时 | 定时备份 + 备用环境，按手册恢复 | 每年 |
| T3 可重建 | 报表、日志、缓存类，可从其他数据重建 | <= 24 小时 | <= 24 小时 | 每日备份或直接重建 | 每年抽查 |

## 2. ops-mall 的分级（示例，按你的业务修改）

| 系统 / 数据 | 级别 | RTO | RPO | 依据 | 当前方案 | 当前能力（演练实测） | 差距 |
|---|---|---|---|---|---|---|---|
| 下单（mall-api + MySQL orders） | T1 | 30 分钟 | 5 分钟 | 下单中断每分钟损失约 x 元；订单丢失要人工补单 | MySQL 主从 + 手动切换；全备 + binlog 每 5 分钟上传 MinIO | | |
| 商品浏览（mall-api + Redis 缓存） | T1 | 30 分钟 | 不适用（缓存可重建） | 浏览不可用影响转化 | 多副本 + 缓存失效回源 | | |
| K8s 应用配置（Deployment、Service、Secret 等） | T1 | 30 分钟 | 24 小时 | 配置变更频率低，Git 里有大部分 | GitOps（Lab 08）+ Velero 每日备份 | | |
| 监控数据（Prometheus） | T3 | 24 小时 | 24 小时 | 丢了影响排障但不影响业务 | 不备份，保留 3 天 | | |
| 日志（Loki） | T3 | 24 小时 | 不备份 | 合规要求另议 | 按租户保留 14 / 3 天 | | |
