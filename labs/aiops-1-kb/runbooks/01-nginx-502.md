# 商城返回 502 Bad Gateway 排查

## 1. 现象
- 用户打开 `http://mall.lab.local` 页面能出来，但商品列表加载失败，浏览器开发者工具里 `/api/products` 返回 502。
- 告警：`MallApiHighErrorRate`，或者 Nginx 错误日志里大量 `connect() failed (111: Connection refused) while connecting to upstream`。

502 的意思是"网关自己没问题，但它找的后端没给正常响应"。所以先查后端 mall-api，再查网关配置。

## 2. 先判断在哪一层
| 部署方式 | 网关 | 后端 |
|---|---|---|
| 虚拟机（Lab 02-03） | lab-web1 / lab-web2 上的 Nginx | 同机的 mall-api，`127.0.0.1:8080` |
| K8s（Lab 06 起） | Envoy Gateway，入口 IP 192.168.56.200 | `mall` 命名空间的 mall-api Service |

## 3. 虚拟机部署的排查步骤
在 lab-web1 上执行（lab-web2 同理）：
```bash
# 1) mall-api 进程在不在
systemctl status mall-api --no-pager
# 2) 端口在不在监听
ss -lntp | grep 8080
# 3) 绕过 Nginx 直接请求后端
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/readyz
# 4) 看 Nginx 错误日志里 upstream 报什么
sudo tail -n 50 /var/log/nginx/error.log
```
错误日志关键字和含义：
- `Connection refused`：后端没监听，进程挂了或者端口不对。看 `journalctl -u mall-api -n 100`。
- `upstream timed out (110)`：后端太慢，超过了 `proxy_read_timeout`。转去看《mall-api 接口延迟高排查》。
- `no live upstreams`：upstream 里所有后端都被判定为失败（`max_fails` 达到），等 `fail_timeout` 后会重试。
- `upstream prematurely closed connection`：后端处理中途断开，常见于 mall-api 重启或 panic。

## 4. K8s 部署的排查步骤
在 k8s-master 上执行：
```bash
kubectl -n mall get pod -l app.kubernetes.io/name=mall-api -o wide
kubectl -n mall get endpointslice -l kubernetes.io/service-name=mall-api
kubectl -n mall describe httproute mall
```
- EndpointSlice 里没有任何 ready 的地址：所有 Pod 的 readinessProbe（`/readyz`）都不过。`/readyz` 会检查 MySQL，开了缓存时还检查 Redis，任何一个连不上都返回 503。先看《Redis 不可用导致全站 503》和数据库连通性。
- Pod 在 `CrashLoopBackOff`：转《Pod CrashLoopBackOff 排查》。
- Envoy Gateway 返回的是 503 `no healthy upstream` 而不是 502，这时意思一样：后端没有可用实例。

## 5. 恢复
- 单台后端挂了：先把它从负载均衡摘掉（虚拟机在 upstream 里加 `down` 后 `nginx -s reload`；K8s 不用管，readiness 失败会自动摘除），再处理。
- 刚发布完就 502：优先回滚（`kubectl -n mall rollout undo deploy/mall-api` 或 ArgoCD 回滚），恢复后再查原因。

## 6. 预防
- Nginx upstream 至少两台后端，配置 `proxy_next_upstream error timeout http_502`，单台故障用户无感。
- 发布用滚动更新，`maxUnavailable: 0`，配好 readinessProbe。
