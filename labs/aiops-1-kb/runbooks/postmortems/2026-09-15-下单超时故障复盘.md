# 2026-09-15 大促下单超时故障复盘

## 1. 概要
| 项目 | 内容 |
|---|---|
| 故障级别 | P1 |
| 影响时间 | 20:02 - 20:41，共 39 分钟 |
| 影响范围 | 下单接口 `POST /api/orders` 约 35% 请求超时或返回 500；商品浏览正常 |
| 发现方式 | 告警 `MallApiHighLatency`（P99 > 2s）和 `MallApiHighErrorRate`，20:04 触发 |
| 根因 | 秒杀商品（id=3）单行热点，`SELECT ... FOR UPDATE` 行锁排队，连接池被占满 |

## 2. 时间线
- 20:00 秒杀活动开始，下单 QPS 从平时 5 涨到 180。
- 20:02 下单 P99 升到 8 秒，日志出现大量 `create order failed` 和 `context deadline exceeded`。
- 20:04 告警触发，值班同学按《mall-api 接口延迟高排查》处理，先扩容 mall-api 从 3 副本到 8 副本。
- 20:10 扩容后更糟：MySQL `Threads_connected` 从 80 涨到 165，接近 `max_connections=200`，商品浏览也开始变慢。
- 20:18 DBA 在 `sys.innodb_lock_waits` 看到上百个会话在等同一行（products.id=3）的锁。
- 20:25 决策：把 mall-api 缩回 3 副本，秒杀商品临时下架（库存置 0），其他商品下单恢复正常。
- 20:41 指标恢复，故障结束。

## 3. 根因分析
- 下单事务里先 `SELECT price_cents FROM products WHERE id = ? FOR UPDATE` 锁住商品行，再扣库存、写订单。同一个商品的所有下单请求只能排队一个一个执行。
- 每个排队的请求占着一个数据库连接。mall-api 每个副本连接池上限 20，排队请求很快占满连接池，后续请求等连接超时。
- **扩容是反效果**：副本从 3 加到 8，连接数上限从 60 变成 160，更多请求挤到同一把行锁上，还把 MySQL 总连接数推高，拖慢了其他查询。

## 4. 做得好的
- 告警 2 分钟内触发，值班 5 分钟内响应。
- Runbook 里的 `sys.innodb_lock_waits` 查询帮助快速定位到热点行。

## 6. 经验
- 扩容只对"应用本身是瓶颈"有效；瓶颈在数据库锁、外部依赖时，扩容会放大问题。
- 判断方法：扩容前看 MySQL 的锁等待和连接数，如果连接数已经很高，扩应用之前先找 DBA。
